## Decisions this decomposition makes

1. **A host card is a new status, `host_approval`, with the card in `host_request`.** Unlike the question card (which keeps `running`), a host card must survive the run (parked), must be refused by Approve/Reject, and must not keep the row claimable or leased. The claim predicate stays `queued OR (running AND lease expired)`, so a `host_approval` row is never claimed; `renewLease` renews only `running`, so the follower stops renewing while it keeps reading the worker. `busy()` does not include `host_approval`; `approve`, `send`-as-approve, `reject` and `discardSteps` refuse it with 409 "This chat is waiting for a host card, not a change review"; Stop and Delete handle it explicitly (Stop: deny the live request, `run.stop`, card closed "Stopped before you answered", row `stopped`; Delete: the same, then `Forget`).
2. **Live wait, then parked** (Q-5.1). `run.start.host_live_wait_s` (Go sends 600). While live, the worker's run thread waits in Hermes' approval gate and the row keeps `agent_run_id`. When the live wait ends, the worker resolves the request as deny with the tool result "Paused: waiting for the person's approval", stops the loop after that tool round and ends the run `run.done {turn_exit_reason: "approval_parked", parked: {request_id, tool, args_hash, tool_call_id}}`. Go keeps `host_approval`, sets `host_request.phase = "parked"`, clears `agent_run_id` (no live run), and the worker becomes idle (reapable; its account run slot is free). A parked card expires after the account's approval timeout (default 60 minutes, `agent_chat_settings.host_approval_timeout_minutes`, 10 to 60) through a Go sweep: card closed "Expired, not run", row `idle`. A run lost during a live wait (worker or API died) becomes a parked card, not a failure, because nothing ran: `Lost` and `WorkerExited` park a `host_approval` row instead of failing it.
3. **The answer is fenced, and re-attach is one-shot.** `POST /chats/:id/host-approval {revision, requestId, choice: "once" | "deny" | "chat", device}` commits only when the row is `host_approval` and `host_request.requestId` matches (and, for a live card, `agent_run_id = host_request.run`). Live `once`/`chat`: in one transaction the row goes back to `running` with a fresh lease adopted by the run's follower (the re-attach), then `approval.answer once` is sent with `context.WithoutCancel`; if this process does not follow the run, or the worker acks `ok: false`, the card becomes parked in a fenced save and the answer is applied as a parked answer (below) instead of being lost. Parked `once`/`chat`: the row goes to `queued` with `continuation {tool, args_hash, tool_call_id, requestId, text}`; the claim that starts the next turn clears `continuation` in the same transaction and sends it as `run.start.pre_approved`, plus the turn's user text "You asked to run <description>. The person approved it: run exactly that call now." The worker's gate allows exactly one matching call (existing rule 2). `deny`: live → `approval.answer deny` (the model gets Hermes' "BLOCKED: Action denied by user"), row back to `running`; parked → row `idle`, thread message "Not run: <description>". A second answer gets 409 "This card was already answered".
4. **One card per call.** After a Timely approval passes, Hermes' terminal guard may raise a second approval for the same call (pattern key, not `plugin_rule:timely:<id>`). The worker's approval bridge answers `once` automatically any request raised while a Timely-approved call is executing (same session key and the same approval-context tool call id), logs it, and sends `event approval.auto`; Go never sees a second card. Any other approval request with no Timely-approved call behind it is denied and logged (fail closed). In Full Access the worker calls `enable_session_yolo(session_key)` for the run instead, so Hermes raises none; the hardline floor (`check_all_command_guards`) still refuses in every mode.
5. **Go decides every host call from mode, critical list, account and grants.** `gate.ask` for a host tool: (a) the account is not host-allowed → `block` "This account can't use this computer. Turn it on in the desktop app, Settings → Server." (b) bot run → `block`. (c) the chat is answer-only, Sensitive or no-persist → `block`. (d) MCP server Off → `block`; Ask me first → `approve` in every mode. (e) map the call to a `HostAction` (decision 6) and ask `CriticalHost` with `HostScope{Workspace: working folder, Hosts, Tainted}`. Supervised → `approve`; Auto → `approve` when critical, else `allow`; Full Access with a step-up record → `allow` (worker uses YOLO); Full Access without one → as Auto. (f) An `allow` from Auto or Full is logged as `allowed` with its reason. (g) A matching grant (decision 8) turns `approve` into `allow` except for critical-list items in Auto, MCP Ask me first tools, stdio MCP configs and `execute_code`. The verdict carries the card text Go builds from the real arguments.
6. **Tool → `HostAction` mapping** (Go, `chat/host_policy.go`): `terminal` → `terminal` with the command; `process_manage` → `terminal` (kill/stop is `terminal` with the process's command); `read_file`/`search_files` → `file_read` (allowed without a call to Go inside the account's own skills folder, existing gate rule); `write_file`/`patch` → `file_write`; `execute_code` → `terminal` with the code (always a card in Supervised and Auto, never grantable); `browser_exec`, `browser_cdp`, `browser_dialog` → **always critical in Auto** (item 2 or 3: a script on the signed-in real profile can submit, send or sign in, and a literal check cannot tell), with the URL the arguments name; `vision_analyze` with a host path → `file_read`; MCP tools → `send` when the tool's name or annotations say it sends (send, reply, forward, post, publish, share, invite, upload, `destructiveHint`/`openWorldHint` writes), `file_write`-like `config` for server settings tools, else `fetch` for read-only (`readOnlyHint`) and a non-critical write otherwise. Each of the six critical-list items has a Go test through `gate.ask` in Auto.
7. **Full Access step-up.** Turning a chat or the account default to Full Access needs the step-up: a request through the desktop window (shell token, decision 11) while `full_access_allowed_on = desktop` (default), or, when the account set "any of my devices", the desktop window or a phone with device unlock. The server stores the step-up on the conversation (`full_access {at, device}`); a `full` without one acts as Auto (Q-2.8). The migration sets every stored `full` to `auto` (dummy data). The one-time confirmation names what Full Access lifts (every card for terminal, files, code, browser and MCP; the hardline floor, secrets, account isolation and learning staging stay). Switching to a looser mode never approves waiting cards; a stricter mode applies from the next `gate.ask`.
8. **"Allow for this chat"** (Q-5.1) is a grant stored on the conversation (`host_grants`), never in Hermes. Kind keys: `terminal`: the program, plus the first subcommand for `git`, `gh`, `npm`, `pnpm`, `yarn`, `npx`, `uv`, `pip`, `cargo`, `go`, `make`, `docker`, `kubectl`; a command with a shell operator (`|`, `;`, `&&`, `||`, `>`, `<`, `$(`, backticks, `&`) or `sudo` is never grantable, so `ls` cannot carry `; rm`. `read_file`/`search_files`/`write_file`/`patch`: tool and folder. `browser_*`: tool and host. MCP Can use tools: server and tool. `process_manage`: the program. Grants last for the chat (deleted with it) and are listed on the chat's permission sheet with Remove.
9. **Host-allowed accounts** (Q-5.2): the effective list is `instance_settings.host_accounts` (turned on in the desktop window) united with `TIMELY_AGENT_HOST_ACCOUNTS` (shown as "set by the server", not removable in the UI). No cap. A host-allowed account gets the host toolsets (`terminal`, `file`, `code_execution`, `browser-use`, `browser-cdp`), `terminal.home_mode: real` (Q-5.4), `checkpoints.enabled: true`, `browser.use_real_profile: true` (Q-5.3), its working folder as `TERMINAL_CWD`, project context files when a folder was chosen, and stdio MCP servers. Every other account gets none of them, its self-test fails if its rendered config has any, and the gate blocks them as a second line. The limit (an approved command runs as the host OS user and can read every account's data, the database files and other workers' environments) is recorded in ADR 0026 and the Settings → Server copy.
10. **Working folder.** Per host-allowed account in `instance_settings.host_accounts[].working_dir`, chosen in the desktop window (native folder picker over preload IPC) or left empty. Empty: `TERMINAL_CWD` is the account's `workspace/` and context files stay off. Chosen: `TERMINAL_CWD` is that folder, `skip_context_files=False`, and a context file read is a taint source (plan 9b). `HostScope.Workspace` is the working folder. `HOME` for terminal children is always the real home.
11. **Shell token and the desktop window.** The Electron supervisor makes a random 32-byte `TIMELY_SHELL_TOKEN` per launch and passes it in the API's environment. The renderer never sees it: preload exposes `timelyDesktop.shell.request(op, body)` for a fixed list of operations (`hostAccounts.set`, `hostAccounts.workingDir`, `chat.permission`, `settings.permissions`, `chat.hostApproval`), and the main process sends them to the API on loopback with `X-Timely-Shell-Token` plus the renderer's session. The API accepts the header only with a constant-time match from a loopback remote address; `PUT /instance/host-accounts` without it is 404 (not 401, so the route does not exist for anyone else). A request that carries a valid token is "the desktop window" for the step-up rule and is recorded so.
12. **Step-up for host cards** (Q-5.7). `agent_chat_settings.host_approval_rule`: `devices` (default: any signed-in device; the phone must unlock first) or `desktop` (only the desktop window). The phone runs `expo-local-authentication` before Run once and Allow for this chat and sends `device {kind: "phone", name, unlocked: true}`; the server refuses a phone answer without `unlocked` (403 "Unlock your phone to approve this") and records the device and session on the approval event. Deny never needs unlock. Changing the rule from `desktop` to `devices` needs the desktop window. Device unlock is enforced by the app, not provable to the server (flagged).
13. **Browser** (Q-5.3). `browser_exec`, `browser_cdp`, `browser_dialog` in chat runs of host-allowed accounts only, on the real profile through Hermes' real-profile session (a snapshot copy of the default Chromium profile of the real home, the installed Chrome/Edge binary). The managed floor stops pinning `use_real_profile: false`; the account config sets it for host-allowed accounts and the self-test refuses it anywhere else. The private-target gate rule (1b) and `browser.auto_local_for_private_urls: false` stay. `browser_vault` and `computer_use` stay blocked.
14. **External MCP** (Q-5.6, plan 8.2). Servers live in `agent_mcp_servers` (per account, mode `use | ask | off`, default `ask` when added). The Settings screen lists Hermes' curated catalog (all 66, messaging-category servers included, flagged) plus custom remote URLs for every account and custom stdio commands for host-allowed accounts. A stdio entry is added or changed only through a host card (kind `mcp_server`) showing the exact command, args and env names; Run once records the entry's hash in `approved_hash`; a changed entry needs a new card. Go validates every remote URL on save and again before each spawn (resolving the host; private, loopback, link-local, CGNAT/Tailscale and metadata addresses dropped with a Settings warning). OAuth tokens: encrypted in `agent_secrets` with the provider-key handling, sent in the account settings at spawn (`mcp_tokens`), written to `mcp-tokens/` by `render-account`, read back by the worker on its maintenance tick and at shutdown (`mcp.tokens`), deleted from the home when the worker exits, never backed up; the OAuth callback comes back through Timely's origin. MCP results stay wrapped as untrusted (Hermes) and taint the chat.
15. **Undo this change.** Hermes checkpoints (`checkpoint_manager`) are on for host-allowed accounts (in the account home, regenerable, not backed up, `max_snapshots: 20`). `event tool.completed` and `host.ran` carry the checkpoint id for `write_file`, `patch` and terminal calls Hermes checkpointed; the activity line and the closed host card show "Undo this change" while the checkpoint exists; `POST /chats/:id/host-undo {checkpointId}` sends `checkpoint.restore` and logs `undone`.
16. **Every host action is logged.** `agent_host_events` rows: `requested`, `approved` (with choice, device, session), `allowed` (mode or grant or continuation, with the reason), `denied`, `parked`, `expired`, `auto` (second approval mapped), `ran` (the worker's `host.ran` after the tool ran, with status), `undone`. The exit check (`verify-docs`) asserts every `ran` has an earlier `approved` or `allowed` for the same tool call id (or the continuation's), across the real-worker suites.
17. **Budget exemption.** Agent runs have no Timely time cap (Q-2.3), so nothing in Go counts the wait. Hermes excludes human waits from tool batch deadlines (`approval_human_wait`); the worker proves a live wait longer than the batch deadline does not trip it, and a parked card is outside any run.
18. **Gateway grants per worker.** The CLI gateway's grant becomes one per (worker instance, provider, model), revoked when that worker exits (`agenthost` exit hook), so a terminal child that reaches 127.0.0.1 holds no lasting key (phase 4 flag 9).
19. **TLA+: a third check.** The turn check is already about 26 minutes, so the host card gets its own config, `model/AgentRunHost.cfg` (two lanes plus followers, one step, one host card, no question card), on the same module. It adds the actions AskHost (follower writes `host_approval` in a fenced save), ParkHost, AnswerHostLive (fenced commit + re-attach), AnswerHostParked (queues the continuation), StartContinuation (claim clears `continuation`), ExpireHost, RunHostTool (the worker runs the call), and Stop/Delete/Lost/Approve/Reject on a `host_approval` row; and the properties: HostResolvesOnce, NoHostToolAfterStop, HostNotAProposal (never applied, approved or rejected), NoLeaseOnHostWait (a `host_approval` row is never claimed or counted as leased; at most one follower re-attaches per answer), ContinuationOnce (the approved call runs at most once). Guards with anchors and mutants: `HostAnswerFenced`, `ClaimSkipsHostWait`, `ApproveRefusesHost`, `ContinuationClearedAtClaim`, `StopDeniesHost`.
20. **Safety while building and testing** (non-negotiable for every package). Host tools act on this machine. Tests and live checks point `HOME`, `HERMES_REAL_HOME`, the working folder and the "real" browser profile at throwaway folders under `$HOME/.cache/p5-sandbox` (made and removed by `make agent-host-sandbox` / `make agent-host-sandbox-clean`, which write a throwaway Chrome `--user-data-dir`, a `mimeapps.list` naming it the default browser, and empty dotfiles). Go honours `TIMELY_AGENT_REAL_HOME` (the real home a worker sees) and the short-timer overrides `TIMELY_AGENT_HOST_LIVE_WAIT_S` / `TIMELY_AGENT_HOST_PARK_S` only when `DB_SCHEMA` is set, and refuses `TIMELY_AGENT_REAL_HOME` outside `$HOME/.cache/p5-sandbox`. Destructive commands (`rm -rf`, `chmod -R`, `curl | sh`, the hardline list) are exercised only through the gate with the stub model or the fake worker, and every Python test that reaches the terminal backend runs under an **exec trap** (`tests/exec_trap.py`) that replaces the local backend's spawn with a recorder and fails the test if a destructive command reaches it. Before any browser check, a test asserts the real-profile snapshot source is inside the sandbox. Never the owner's real home, browser profile, `~/.ssh`, `~/.gitconfig` credentials or `~/.hermes`. External MCP servers in tests are local fakes (an stdio echo server and an `httptest` remote served on a public-looking fixture name); no real mail or calendar account, nothing sent.

## Flagged for the coordinator or the owner

1. **`host_approval` is a new status, unlike the question card** (decision 1). It is needed for the parked card and the Approve/Reject refusal, and it costs a third TLA+ check (decision 19).
2. **A typed message does not answer a host card** (unlike a question card): it queues as the next turn. A message cannot mean "run it".
3. **"Allow for this chat" kinds** (decision 8): program plus subcommand for a fixed list, folder for files, host for the browser, server and tool for MCP; a command with a shell operator or `sudo` and every `execute_code` call always ask; a grant never covers critical-list items in Auto or Ask me first tools.
4. **Auto asks for every browser call** (decision 6): on the real signed-in profile a script can send, buy or sign in, and the gate cannot tell from the arguments. A looser rule (navigate-and-read on a known host runs) is possible if the owner wants fewer cards.
5. **MCP "sending" is classified by tool name and annotations** (decision 6); a server that hides sending behind a neutral name runs in Auto under Can use. Ask me first is the safe setting for a mail server.
6. **The whole catalog, messaging-category MCP servers included** (Q-5.6 read as amending decision 6 for all external MCP servers). Hermes' messaging platform adapters stay excluded.
7. **Device unlock is enforced by the phone app** (decision 12): the server records the device's `unlocked` claim but cannot verify it; a stolen signed-in session on a plain web browser can approve under the "any device" rule (Q-5.7). The "Only the desktop window" rule is the stricter option.
8. **Several host-allowed accounts share one machine and the real home** (Q-5.2, Q-5.4): each can read the others' data through an approved command. Settings → Server says so when a second one is turned on.
9. **A stored `full` becomes `auto`** (decision 7, Q-2.8): Full Access needs a fresh step-up after this phase.
10. **Lost or crashed live waits park instead of failing** (decision 2): nothing ran, so the card stays answerable for its timeout.
11. **Approval timeout range 10 to 60 minutes, default 60** (Q-5.1's "up to 1 hour"); the live wait is fixed at 10 minutes.
12. **Working folder per account, chosen in the desktop window** (decision 10); a per-chat folder is possible later.
13. **The real-profile browser on Linux** depends on Hermes resolving the default browser from the (sandboxed) home; `worker-host` proves it in the sandbox, and a desktop without a supported Chromium default gets Hermes' signed-out fallback note.
14. **Docker images run host tools inside the container** (plan 11.5); nothing changes there in phase 5, and the copy says "this server" there rather than "this computer".
