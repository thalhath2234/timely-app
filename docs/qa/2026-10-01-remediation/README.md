## Investigations from the audit's remaining checks

### Android sheet: cell draft lost on leaving the screen — confirmed and fixed

Confirmed by code and by the fix behaving as expected on the device. `SheetGrid` committed a draft only on blur or Enter; popping the screen fires neither, and the leave guard only tracked the parent's autosave state, so a draft typed in the formula bar or in a cell was dropped when the user tapped the header Back or the system Back.

Fix: `SheetGrid` exposes `commitActiveEdit` through a `ref` (`SheetGridHandle`). The sheet screen counts an active draft as unsaved, and `useUnsavedLeaveGuard` gained a `beforeLeave` hook: on an intercepted leave the screen commits the draft, flushes the autosave, and leaves without a confirmation; the confirmation only appears if that save fails. Header Back commits the draft before navigating. Docs keep their previous behaviour.

Controlled comparison on the emulator against the server value ([android-sheet-draft-cells.txt](evidence/android-sheet-draft-cells.txt)):

| Draft source | Leave by        | Server value after leaving |
| ------------ | --------------- | -------------------------- |
| formula bar  | header Back     | `hb` saved                 |
| formula bar  | system Back     | `sb` saved                 |
| formula bar  | Enter           | `En` saved                 |
| formula bar  | blur (tap cell) | `bl` saved                 |
| in cell      | header Back     | `icx` saved                |
| in cell      | system Back     | `sy` saved                 |

No "Unsaved changes" confirmation appeared in any case because every flush succeeded. The pre-fix loss was not re-reproduced on the device in this session: Metro ran in CI mode (no watch), so swapping the bundle back was not practical; the audit's observation and the code path are the evidence for the original behaviour.

### Android agenda scrolling — not a product bug

With 30 Events across 10 days the agenda scrolled to "Sat, Oct 10 · Agenda 10-16h"; the last item opened its sheet and the header navigation (Previous, Today, Next, view switcher) stayed in place ([android-agenda-top.png](evidence/android-agenda-top.png), [android-agenda-bottom.png](evidence/android-agenda-bottom.png), [android-agenda-last-open.png](evidence/android-agenda-last-open.png)). Swipes that started on the dismissible "Meet your assistant" toast did not scroll the list; that overlay sits over the lower rows until "Got it" is tapped, which is worth knowing for future device checks but is not a scrolling defect. No code change.

Launching the APK on the emulator is not possible: the x86_64 image resolves in-APK native libraries under `lib/x86_64`, which an arm64-only build does not contain, and SoLoader aborts with `couldn't find DSO to load: libreactnative.so`. The September 26 APK built from the audited dependencies fails identically on the same image, so this is the image, not the upgrade ([apk-emulator-launch.txt](evidence/apk-emulator-launch.txt)). Runtime validation of the release build still needs an arm64 phone (`make install-apk`); the JavaScript and native module changes were exercised in Expo Go above.

## New finding fixed during remediation

- **QA-08 — missed-Block and start-soon notifications never enqueued.** The API log on 8081 repeated `jobs sweep: ERROR: new row for relation "jobs" violates check constraint "jobs_kind_check"` once a minute. The code enqueues `missed_block` and `start_soon` jobs and writes `missed` and `start` notifications, but the constraints written by `migrations/20260923132908_allow_overdue_notifications.sql` and `20260928120602_agent_notification_category.sql` never learned those values, so every insert failed and no missed-Block or start-soon notification could ever be delivered. Fixed by the migration above; the regression test compares the newest constraint in the migrations with the model constants so the two cannot drift again. The migration version is dated after the shared development database's current version so goose applies it in order.
