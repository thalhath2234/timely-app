# Smart suggestions run on Jev through one decision service, and only suggest

- Status: Accepted
- Date: 2026-10-09

Timely asks small typed questions ("Is this Work or a Reminder?", "How much effort does this take?", "Is this the same task as that one?") of Jev, TypeSafe's decision model, instead of a chat model. Jev answers a Choice, a Score or a yes/no with a confidence, in well under a second, which fits places where a chat model is too slow or too costly: the Clarify form, the agent's default work length, and later the scheduler and notifications.

**One service in the API.** `internal/features/decide` is the only code that talks to Jev. Features build questions with `decide.Choice`, `decide.Score` and `decide.YesNo` and read answers with a minimum confidence (`Prefill` 0.6, `Route` 0.8, `Flag` 0.5). Below the threshold a feature behaves as if Jev had said nothing. The service shuffles choice options and can ask a question twice in reversed order (`Twice`), treating disagreement as zero confidence, to blunt Jev's first-option bias. It caches identical requests for ten minutes, caps parallel calls per account, keeps state under 32 KB, and logs one `decision_log` row per call (feature, provider, latency, whether the person kept the suggestion) without the text. Rows older than 30 days are pruned.

**Keys are per account, TypeSafe first.** A TypeSafe key saved in Settings → Agent is used first. On a 401, 429, 529, 5xx or network error the same request goes to OpenRouter's Decisions API (`typesafe/jev-1.13`) with the account's existing OpenRouter key; TypeSafe is Jev's only provider there, so no other company sees the request; a 422 is the request's fault and does not fall back. A 401 marks the TypeSafe key as refused until it is replaced, so later calls go straight to OpenRouter. With neither key, or with the switch off, every feature returns nothing and the app works exactly as it did before. A call that fails is logged by the API and named in the Clarify form, and Settings → Agent has a Test button that makes one live call.

**In Clarify, code reads the date and Jev names its role.** When an Inbox item's words hold a date ("tomorrow at 3pm", "next friday", "3 Nov", "in a week"), code reads it in the person's own day and Jev only says whether it is a deadline, a start date or a reminder time (Prefill); the form fills that one field if the person has not touched it, and an unreadable date only points at the field as before. The New Work forms offer the agent's estimate as a suggested length the person can click.

**In agent chat, Jev only narrows and warns.** Before the model's first call on a new message, one triage call (1.5 s budget) names the area of the request, whether it is a question or a change, whether it needs the web, whether it is too unclear to act on, which occurrences of a repeating item it means, its language when the script alone cannot tell, and, for a new chat, an earlier chat about the same request. The area narrows the read tools offered; the others stay callable by name and the run offers everything again as soon as one is called. The rest become a notice the model is told it may ignore, a conversation language for Timely's own notices, and a "You already have a chat about this" pointer. At that pointer the new chat stops before the model runs and waits for the person (status "choose", listed under "Needs you"): "Continue there" moves the message into the earlier chat, runs it there and deletes the new chat; "Answer here" runs it where it is. After a proposal is prepared, one check asks whether each step was requested and whether something requested is missing; any such note is shown on the review and forces a review even for a change that would have applied directly. When a chat has several attached items, one more call alongside triage asks, for each long one (unsaved drafts excluded), whether this message needs it; one Jev is sure about (Route) is sent as its label and a short preview marked "attached but probably not needed", never dropped. When Jev has a key, the model is also offered resolve_target for a change that names an item that may match several ("move my dentist appointment"): code shortlists up to eight items of that kind by search, with event and task dates written in words, and Jev picks the one the request means (asked twice, Route), returned first as the pick; with no confident pick the shortlist keeps its order and the model asks as before, and the proposal is built and reviewed exactly as without it. Whether the proposal then names the pick or another candidate is the feedback. Sensitive chats are never sent.

**In search, Jev only reorders and suggests.** GET /search/smart runs the usual hybrid search, then one call asks yes/no for each of the top 10 results ("could this be what they are looking for?"), which kind of item is wanted, and whether the query is really a command ("make a budget sheet"). Results are sorted by Jev's yes probability; only a confident no (Route) moves a result to a "weak matches hidden" list the person can open. Screens show the plain results first and apply this answer when it arrives, only for the query still on screen. The agent's semantic_search gets the same reordering and, when every result is a clear miss, is told to search again rather than build on a wrong item. GET /search/related takes the nearest items by embedding (the mean of the item's own chunk vectors, so no embedding call) and keeps those Jev confirms are about the same thing; with Jev or embeddings off the list is empty and hidden.

**On receipts and sheets, Jev only pre-fills and notes.** Receipt chats are private, so a receipt question carries only names (the merchant, item names, the person's own categories, sheet, tab and column names), never the photos, the extracted text or any amount (numbers in the person's typed message and in column examples are masked), and OpenRouter is asked for zero-data-retention endpoints (`provider.zdr`). After a receipt is read, one call (3 s budget) picks one of the person's existing categories when the extracted one is not theirs (the category stays editable, and a correction the person typed is never overridden), checks that a known category fits, asks whether it is a refund, whether a recorded receipt with the same total a few days apart (or under another merchant name) is the same purchase, and which expense tab it belongs in; the answers become non-blocking hints on the review and a pre-selected destination that an open or attached sheet still overrides. Whether the totals reconcile once tax or the discount counts as included is arithmetic, so code checks it and shows it with those hints. A chat message during review that Jev is sure changes nothing in the draft skips the model call. When the chosen tab has no column for a field by name, Jev may match an existing one ("Shop" for Merchant), kept only when it agrees in both option orders and the column's type fits. For agent chat, an update_sheet step is described in code (columns added, removed, renamed or retyped, rows added, removed or edited) and Jev is asked whether that matches the request; a mismatch is a review note. A new sheet's title can pre-pick one of the person's saved templates until they pick one, and an imported CSV column can take a type, chosen only among the types every value already fits (dates only as YYYY-MM-DD). When the person types a new entry into a text column whose header names a kind of thing (Category, Merchant, City, Status and similar) or into a select column, and the entry is not already in that column, one question a moment after the edit (asked twice, Flag) asks whether it is the same kind of thing as the header and up to eight of the column's other values (numbers masked); a no is a dismissible "This may not fit the Category column" line by the sheet's status bar on the web and under the formula bar on the phone, and the cell is never changed. A wrong type in a typed column is code's job and never asked. Which extracted amount is subtotal, tax or total, and whether a field is supported by the source text, are left out: the only source text is the same model's reading of the photo.

**On Work and projects, Jev reads words and code keeps the numbers.** A task's panel asks one batched call about its own title, description, latest comments and checklist: which of the workspace's statuses it reads like (asked twice, Route), which stage of its project it belongs in, the values of empty select, multi-select and yes/no fields the description states, whether it waits on one of a few nearby open tasks (candidates that already wait on it, directly or down the chain, are never offered, so a suggestion cannot close a loop), whether its outcome is vague, whether the description asks for something the checklist misses, and, once complete, whether its words say something is left; unchecked checklist items on a completed task are counted in code. Each suggestion is applied by the person, one at a time. Stale Work lists open tasks with no edits, comments or upcoming Blocks for three weeks (recurring tasks left out, idle days counted in code) and asks what each one needs (still worth doing, needs clarifying, waiting, maybe no longer needed); "Keep" records a review activity that restarts the count. The agent's pick_tasks takes a bulk edit described in words, searches up to 40 tasks and asks yes/no per task; matches and unsure ones come back for review before bulk_update_tasks, which now sends sets above 50 in batches. A project's insights count open, done, overdue and blocked Work and the days since any activity, then ask about its health, a brief with no outcome or no next step, list items of the brief no task covers, tasks that look filed in the wrong project (a second call picks a better project) and overlapping projects. Labels, statuses or select options that may mean the same are paired in code (similar names, or every pair of a short list) and Jev only answers yes/no per pair; the kept side is the one more Work uses, and the merge, which the person confirms, moves tasks, projects and saved views over in one transaction. A new project's title can suggest an earlier project to copy and a doc or sheet template, offered unticked. A repeating task copied by Start from keeps its rule and starts its series on the new project's start (or today), on the first day the rule falls on; a series with an end date keeps its number of occurrences, counted in code with the recurrence rule, so a monthly series of two runs twice again.

**In docs, Jev picks among what code offers.** A doc's suggestions are one batched call made when the page opens and again as it grows. For a doc with text it asks which of the workspace's open projects it was written for and which nearby page (by semantic search, never the doc itself or one of its sub-pages, templates or daily notes) it is a part of, both read at Route and asked only while the doc has none; the doc's type among meeting notes, plan, reference, journal and spec unless the person already uses a "type" property; values for property keys that at least two of their other docs share, chosen only among the values those docs use; and yes/no per short paragraph or list item (headings, code, tables and checked items left out, and lines that already name open Work dropped) for "something to do", each turned into a task only when the person clicks. A doc left alone for 30 days is also asked whether it looks outdated, with today's date and "edited 3 months ago" written out in words so Jev never compares dates. A near-empty doc is asked only which of the person's templates it follows. A whole doc can now be moved under another page from its right-click menu. Selected text can become a mention: semantic search finds up to six tasks, projects, docs and sheets, and Jev's pick (asked twice, Route) is shown first above the others. The phone offers the same as "Link to an item" on a text selection in the doc editor, and its doc suggestions card can set the suggested type and property values in the doc's Properties block, as the web does. A plain-text import with no Markdown in it (3 to 80 lines) gets a block type per line (heading, bullet, numbered, quote or paragraph); the client turns those into Markdown markers and falls back to the plain import on any failure. For agent chat, a create_doc, update_doc or append_to_doc step that writes text (at most three per proposal) adds its draft to the review call, which asks whether it leaves out something the person asked for or breaks an instruction about it, and, for an edit, whether it contradicts what the doc says now; either is a review note. When the agent reads a doc of 12 KB or more with get_doc's focus (what it is looking for), code splits the doc at its headings and one call asks yes/no per section, from its heading and first words, whether it is about that focus (Flag); the other sections come back as one [section kept out ...] line each, which keeps the section unchanged when written back, and full=true, no focus, a sensitive chat or no section marked relevant return the whole doc. A placeholder line that was changed (a list marker, an indent, backticks or other text around it) fails the write with a note to keep it exactly or read the doc with full=true, so a section is never saved as a stub. A proposal shows those sections in full, so the person and the draft review see what will be written, and a focused read also records the whole doc's version, so an edit made after it stops the proposal as for a plain read.

**On Today and in Auto-schedule, code finds the time and Jev reads the words.** Each open task's kind of effort (deep focus, admin, creative, routine) and how urgent its own words make it (a 0 to 4 Score) are read once and stored on the task with a hash of its title and description, so Preview, Apply and Undo rank the same way and a changed task is read again. They are filled for the top 12 Unscheduled or Overdue tasks before each Auto-schedule Preview the person or agent asks for (4 s budget, paused for two minutes after a timeout; Apply, Undo and Capacity never ask), when Today's suggestions load, and when a task's panel opens. The same call asks which other task in that set shares a topic, place, person or tool; picks at Route are joined into groups keyed by their smallest task id. Urgency moves a task's rank by (level − 2) × 6, at most 12 points, less than one priority step, with "sounds urgent" or "sounds like it can wait" among its reasons in what_next and Auto-schedule. A group member ranked within 10 points of the group's first task is placed right after it. Today's suggestions take the top 12 ranked tasks that are not blocked, repeating or already in focus and ask how much each matters today (Score, levels 2 and 3 shown, at most three), which of the person's goals (Settings → Agent, up to five, in their words) each moves forward, and, for the next free gap of at least 20 minutes today (found by code), which task that fits it is the best use of it given the time of day and the person's best time for deep work. "Add to focus" and "Schedule here" are the person's clicks. A task's panel also asks whether a task of 90 minutes or more needs one unbroken stretch (offering "one sitting") and, for deep-focus work with no preferred window, offers the person's best time of day, clipped to their working hours, as one. A missed block or overdue notification asks which next step fits (overdue: reschedule as urgent, move the deadline a week, lower the priority, with the days past the deadline from code; missed: add time, move the rest to the next free time, lower the priority) and names it in the text and as a highlighted step, filled in after the notification is sent so reminders never wait on the model; every step runs only when the person taps it, and moving or adding time changes nothing when the engine finds no room. In agent chat, triage also asks whether a message about an event wants time blocked to prepare, the event added, or a reminder before it, as one more line of the notice.

**In notifications and on the Dashboard, code counts and Jev picks.** Once a day, from the morning digest time, a smart alerts job (Settings → Notifications → Smart alerts, on by default) gathers up to ten candidates in code: Work due within three days with no time on the calendar, Work a task finished in the last three days was blocking, a project due within a week that still has open Work, three or more Inbox items waiting three days or more, and the stalest idle Work. Dates become words ("due tomorrow", "finished yesterday") before Jev sees them. One call asks yes/no per candidate whether it deserves an alert today (Flag), which next step fits (review, clarify, add to today's Focus, find time; read at Flag, else the code's default for that kind) and which other candidate is about the same project or issue (Route); joined candidates become one alert listing their Work, and at most three alerts go out, most likely first. Work alerted about in the last seven days is left out, each alert is sent once a day, and its step runs only when the person taps it (Focus and Find time act; Review and Clarify open the Work and mark the alert read). An alert deleted (its own dismiss button or DELETE /notifications/:id) or cleared without its step counts as a suggestion not kept, once per decision and never over a kept answer, so learned defaults raise the bar for smart alerts; opening one or marking it read is neutral. Dismissed alerts are hidden rather than deleted (kept 30 days, still counted in the quiet week), and a kind of alert (due, unblocked, project, inbox, stale) dismissed on three different days in 14 (one Clear all counts once) with no step taken on one of that kind in those 14 days is left out of the daily run, counted in code, until those dismissals age out. Old dismissed alerts are pruned by the notification sweep once a day whether or not smart alerts are on, and a dismissed alert's deferred push is never sent. The morning briefing lists up to twelve of the day's items (Focus, Overdue Work with days past the deadline, events and planned Work with their times, Unscheduled Work due within two days), asks yes/no per item whether a short briefing should name it, and starts the text with "Top today:" and up to three names; the briefing is sent after that call, in the background, or as before when there is nothing to pick. The Dashboard's Highlights card computes its facts in the client (tasks finished this week against last week, streak, overdue, due this week, open Work, the weekday most gets done, the Inbox) and sends them as sentences; the server adds blocked Work (waits on an open task, or a status named like "blocked" or "waiting") and Work whose planned time passed in the last two weeks while still open. A first call sorts the blocked Work into themes (waiting on someone, missing information, approval or money, tools or access, other work first, next step unclear) and the unfinished Work into reasons (bigger than planned, interrupted, blocked, unclear, put off), counted in code; a second call scores how worth highlighting each fact is (levels 2 and up, at most three) and keeps at most two of eight fixed tips that the person's facts back (Prefill). Jev never writes a fact or a tip; it only chooses among them.

**For onboarding and personalisation, code writes the options and Jev fits them to the person.** Onboarding asks "What will you use Timely for?" (work, personal life, study, a business, leading a team, creative work, health, home); the picked uses choose starter labels from a fixed catalog in code, shown ticked and created with the first workspace, so it works before any key is saved; each picked use also offers a workspace name (Work, Personal, Study and so on), the first naming the workspace unless the person types one and the others created alongside it only when ticked. The uses are stored as the person's own words (Settings → Agent → What you use Timely for, editable). Later, a workspace's Labels settings ask yes/no per catalog label whether it would help sort that workspace's Work, given those words, its existing labels and its 25 most recent open tasks (Flag, at most eight shown); names already used anywhere are left out because label names are unique, and nothing is created until the person clicks Add. Each of Today, Tasks, Calendar and the Inbox can show one tip: code holds the tips and when each applies (overdue Work, no working hours, an Inbox piling up, few saved views and so on, with the counts in the text), and Jev picks the one that helps most on that screen or none (asked twice; since every offered tip is true, the two orders agreeing is enough, read at 0.3); a dismissed tip never comes back. The empty assistant chat shows four example prompts written in code from a project's state (its name, largest task, overdue, blocked or unplanned Work), the project on screen or else the one worked on most recently, and Jev scores which would help most now; the rest are filled in code order. Smart search offers the person's saved task views (their filters described in words by code) when a query of two words or more reads as asking to see a list, and opens the view Jev picks (asked twice, Route). Learned defaults: each feature's last 20 answered suggestions are counted from the decision log; with at least eight, keeping fewer than 40% raises every reader's minimum confidence for that feature by 0.15, fewer than 20% by 0.3 (at most 0.95; readers asking for any confidence are unchanged), cached for ten minutes and dropped on new feedback. Settings → Agent lists what each feature learned, with a Reset that forgets those answers.

**Suggest, never act.** Jev output only pre-fills fields the person has not touched, adds hints, or picks a default the person can change before saving (for example the agent's estimate for new Work, which the New Work forms also offer as a suggested duration). Nothing is created, moved or deleted because Jev said so. The one thing Jev writes is a task's stored traits (effort, urgency, group), which only nudge the order Auto-schedule and what_next use; priority, deadlines and pins still decide. Dates, numbers and counts are never read from Jev (it is weak at them); it picks a bucket in words and code maps the bucket to a value.

## Considered Options

- **Use the chat model for these questions**: rejected; a chat round trip is seconds and tokens for what is a one-word answer, and its output needs parsing.
- **Let each feature call Jev itself**: rejected; key order, fallback, caching, rate limits and logging would be repeated and drift.
- **Auto-apply high-confidence answers**: rejected for now; a wrong silent change costs more trust than a pre-filled field saves, and the feedback log is what would justify any later change.
- **A server-wide Jev key in `.env`**: rejected; keys follow the per-account model of ADR 0009.
