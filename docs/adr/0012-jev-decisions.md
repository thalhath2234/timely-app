# Smart suggestions run on Jev through one decision service, and only suggest

- Status: Accepted
- Date: 2026-10-09

Timely asks small typed questions ("Is this Work or a Reminder?", "How much effort does this take?", "Is this the same task as that one?") of Jev, TypeSafe's decision model, instead of a chat model. Jev answers a Choice, a Score or a yes/no with a confidence, in well under a second, which fits places where a chat model is too slow or too costly: the Clarify form, the agent's default work length, and later the scheduler and notifications.

**One service in the API.** `internal/features/decide` is the only code that talks to Jev. Features build questions with `decide.Choice`, `decide.Score` and `decide.YesNo` and read answers with a minimum confidence (`Prefill` 0.6, `Route` 0.8, `Flag` 0.5). Below the threshold a feature behaves as if Jev had said nothing. The service shuffles choice options and can ask a question twice in reversed order (`Twice`), treating disagreement as zero confidence, to blunt Jev's first-option bias. It caches identical requests for ten minutes, caps parallel calls per account, keeps state under 32 KB, and logs one `decision_log` row per call (feature, provider, latency, whether the person kept the suggestion) without the text. Rows older than 30 days are pruned.

**Keys are per account, TypeSafe first.** A TypeSafe key saved in Settings → Agent is used first. On a 401, 429, 529, 5xx or network error the same request goes to OpenRouter's Decisions API (`typesafe/jev-1.13`) with the account's existing OpenRouter key; TypeSafe is Jev's only provider there, so no other company sees the request; a 422 is the request's fault and does not fall back. A 401 marks the TypeSafe key as refused until it is replaced, so later calls go straight to OpenRouter. With neither key, or with the switch off, every feature returns nothing and the app works exactly as it did before. A call that fails is logged by the API and named in the Clarify form, and Settings → Agent has a Test button that makes one live call.

**In agent chat, Jev only narrows and warns.** Before the model's first call on a new message, one triage call (1.5 s budget) names the area of the request, whether it is a question or a change, whether it needs the web, whether it is too unclear to act on, which occurrences of a repeating item it means, its language when the script alone cannot tell, and, for a new chat, an earlier chat about the same request. The area narrows the read tools offered; the others stay callable by name and the run offers everything again as soon as one is called. The rest become a notice the model is told it may ignore, a conversation language for Timely's own notices, and a "You already have a chat about this" pointer. At that pointer the new chat stops before the model runs and waits for the person (status "choose", listed under "Needs you"): "Continue there" moves the message into the earlier chat, runs it there and deletes the new chat; "Answer here" runs it where it is. After a proposal is prepared, one check asks whether each step was requested and whether something requested is missing; any such note is shown on the review and forces a review even for a change that would have applied directly. Sensitive chats are never sent.

**In search, Jev only reorders and suggests.** GET /search/smart runs the usual hybrid search, then one call asks yes/no for each of the top 10 results ("could this be what they are looking for?"), which kind of item is wanted, and whether the query is really a command ("make a budget sheet"). Results are sorted by Jev's yes probability; only a confident no (Route) moves a result to a "weak matches hidden" list the person can open. Screens show the plain results first and apply this answer when it arrives, only for the query still on screen. The agent's semantic_search gets the same reordering and, when every result is a clear miss, is told to search again rather than build on a wrong item. GET /search/related takes the nearest items by embedding (the mean of the item's own chunk vectors, so no embedding call) and keeps those Jev confirms are about the same thing; with Jev or embeddings off the list is empty and hidden.

**On receipts and sheets, Jev only pre-fills and notes.** Receipt chats are private, so a receipt question carries only names (the merchant, item names, the person's own categories, sheet, tab and column names), never the photos, the extracted text or any amount (numbers in the person's typed message and in column examples are masked), and OpenRouter is asked for zero-data-retention endpoints (`provider.zdr`). After a receipt is read, one call (3 s budget) picks one of the person's existing categories when the extracted one is not theirs (the category stays editable, and a correction the person typed is never overridden), checks that a known category fits, asks whether it is a refund, whether a recorded receipt with the same total a few days apart (or under another merchant name) is the same purchase, and which expense tab it belongs in; the answers become non-blocking hints on the review and a pre-selected destination that an open or attached sheet still overrides. Whether the totals reconcile once tax or the discount counts as included is arithmetic, so code checks it and shows it with those hints. A chat message during review that Jev is sure changes nothing in the draft skips the model call. When the chosen tab has no column for a field by name, Jev may match an existing one ("Shop" for Merchant), kept only when it agrees in both option orders and the column's type fits. For agent chat, an update_sheet step is described in code (columns added, removed, renamed or retyped, rows added, removed or edited) and Jev is asked whether that matches the request; a mismatch is a review note. A new sheet's title can pre-pick one of the person's saved templates until they pick one, and an imported CSV column can take a type, chosen only among the types every value already fits (dates only as YYYY-MM-DD). Which extracted amount is subtotal, tax or total, and whether a field is supported by the source text, are left out: the only source text is the same model's reading of the photo.

**On Work and projects, Jev reads words and code keeps the numbers.** A task's panel asks one batched call about its own title, description, latest comments and checklist: which of the workspace's statuses it reads like (asked twice, Route), which stage of its project it belongs in, the values of empty select, multi-select and yes/no fields the description states, whether it waits on one of a few nearby open tasks (candidates that already wait on it, directly or down the chain, are never offered, so a suggestion cannot close a loop), whether its outcome is vague, whether the description asks for something the checklist misses, and, once complete, whether its words say something is left; unchecked checklist items on a completed task are counted in code. Each suggestion is applied by the person, one at a time. Stale Work lists open tasks with no edits, comments or upcoming Blocks for three weeks (recurring tasks left out, idle days counted in code) and asks what each one needs (still worth doing, needs clarifying, waiting, maybe no longer needed); "Keep" records a review activity that restarts the count. The agent's pick_tasks takes a bulk edit described in words, searches up to 40 tasks and asks yes/no per task; matches and unsure ones come back for review before bulk_update_tasks, which now sends sets above 50 in batches. A project's insights count open, done, overdue and blocked Work and the days since any activity, then ask about its health, a brief with no outcome or no next step, list items of the brief no task covers, tasks that look filed in the wrong project (a second call picks a better project) and overlapping projects. Labels, statuses or select options that may mean the same are paired in code (similar names, or every pair of a short list) and Jev only answers yes/no per pair; the kept side is the one more Work uses, and the merge, which the person confirms, moves tasks, projects and saved views over in one transaction. A new project's title can suggest an earlier project to copy and a doc or sheet template, offered unticked.

**In docs, Jev picks among what code offers.** A doc's suggestions are one batched call made when the page opens and again as it grows. For a doc with text it asks which of the workspace's open projects it was written for and which nearby page (by semantic search, never the doc itself or one of its sub-pages, templates or daily notes) it is a part of, both read at Route and asked only while the doc has none; the doc's type among meeting notes, plan, reference, journal and spec unless the person already uses a "type" property; values for property keys that at least two of their other docs share, chosen only among the values those docs use; and yes/no per short paragraph or list item (headings, code, tables and checked items left out, and lines that already name open Work dropped) for "something to do", each turned into a task only when the person clicks. A doc left alone for 30 days is also asked whether it looks outdated, with today's date and "edited 3 months ago" written out in words so Jev never compares dates. A near-empty doc is asked only which of the person's templates it follows. A whole doc can now be moved under another page from its right-click menu. Selected text can become a mention: semantic search finds up to six tasks, projects, docs and sheets, and Jev's pick (asked twice, Route) is shown first above the others. A plain-text import with no Markdown in it (3 to 80 lines) gets a block type per line (heading, bullet, numbered, quote or paragraph); the client turns those into Markdown markers and falls back to the plain import on any failure. For agent chat, a create_doc, update_doc or append_to_doc step that writes text (at most three per proposal) adds its draft to the review call, which asks whether it leaves out something the person asked for or breaks an instruction about it, and, for an edit, whether it contradicts what the doc says now; either is a review note.

**Suggest, never act.** Jev output only pre-fills fields the person has not touched, adds hints, or picks a default the person can change before saving (for example the agent's estimate for new Work). Nothing is created, moved or deleted because Jev said so. Dates, numbers and counts are never read from Jev (it is weak at them); it picks a bucket in words and code maps the bucket to a value.

## Considered Options

- **Use the chat model for these questions**: rejected; a chat round trip is seconds and tokens for what is a one-word answer, and its output needs parsing.
- **Let each feature call Jev itself**: rejected; key order, fallback, caching, rate limits and logging would be repeated and drift.
- **Auto-apply high-confidence answers**: rejected for now; a wrong silent change costs more trust than a pre-filled field saves, and the feedback log is what would justify any later change.
- **A server-wide Jev key in `.env`**: rejected; keys follow the per-account model of ADR 0009.
