Lessons from building the self-contained desktop bundle on 2026-10-03 (ADR 0011, docs/desktop/README.md).

- Next `output: standalone` bakes `rewrites()` into the build. The desktop app's API port is dynamic, so Electron builds (`ELECTRON_BUILD=1`) return no rewrite and `apps/web/app/api-proxy/[...path]/route.ts` proxies at runtime from `API_ORIGIN`. Symptom when this is wrong: the packaged app silently talks to the dev API on 8080 (login "invalid email or password" while `/health` looks fine).
- zonky embedded-postgres jars ship only `initdb`, `pg_ctl`, `postgres`. Backups are cold folder copies of PGDATA (`supervisor/backup.ts`), taken before Postgres starts on upgrade and after a fast stop for "Back up now". Stop Postgres with SIGINT (fast); SIGTERM (smart) waits 10 s for the API's idle pool connections.
- Stage dir names follow electron-builder macros: `linux-x64`, `mac-arm64`, `win-x64` (not `darwin-`/`win32-`).
- Hosted-mode test on this machine: `make stage-desktop`, then from apps/web `TIMELY_USER_DATA=$PWD/tmp/hosted-userdata xvfb-run -a node electron/hosted.mjs --no-sandbox --ozone-platform=x11 --remote-debugging-port=4062`; drive it with `@playwright/test` `chromium.connectOverCDP` from a script inside the repo (bare `playwright` is not installed). Default ports 54329/48080/44001. Find the main process with the `[h]osted-userdata` pgrep trick and skip `--type=` children; a pattern that appears in your own command line kills your own shell.
- Expo SDK 57 has no `android.usesCleartextTraffic` field: the app.json key is silently ignored and Android blocks plain `http://` to the Tailscale address (phone shows "Could not reach …" for every URL). `apps/mobile/app.config.js` sets it with a `withAndroidManifest` plugin; verify with `expo config --type introspect`. The AppImage needs FUSE (`fuse2` on Arch) or `--appimage-extract-and-run`.
- Claude Code as the Agent provider (`provider/claude.go`, `claude -p --tools ""`) sometimes calls Timely tools natively anyway; the CLI answers `No such tool available` and the model tells the person "the lookup failed twice" / "the proposal step isn't available on my end". It is random per run, not client-specific (looked like phone-only on 2026-10-03). `readStream` now turns those rejected `tool_use` blocks into the turn's tool calls. Reproduce by replaying a prompt through `Complete` several times.
- Release pipeline (`.github/workflows/release.yml`, first full run 2026-10-04 for v0.1.1): only Linux built. Causes: (1) `actions/cache` keys cannot contain commas, and the mac target is `darwin-x64,darwin-arm64` (key now uses `runner.os`); (2) `android-actions/setup-android@v3` installs the removed `tools` package by default and always fails (use `@v4`); (3) Node 22.17+ `fs.cpSync` without a `filter` uses a native fast path that aborts the process on Windows filesystem errors (nodejs/node#63970); MSYS bash reports any unknown Windows crash status as exit 127 with no stderr. `stage-next.mjs` passes `filter: () => true` to stay on the JS copier.
- electron-builder drops the root `node_modules/` of every `extraResources` directory (app-builder-lib `util/filter.js`), and it does NOT dereference symlinks: Node's cpSync rewrites the relative pnpm links in `.next/standalone` to absolute build-machine paths, and they ship as-is. v0.1.1 (AUR `timely-bin`) shipped `apps/web/node_modules/next -> /home/runner/work/...` and failed with "Cannot find module 'next'" / "Starting app exited with code 1". Local smoke tests passed only because the absolute link resolved into the local repo. Since 2026-10-04 `stage-next.mjs` rebuilds `apps/web/node_modules` as a flat tree of real dirs (BFS over pnpm siblings) and fails the build if any symlink remains. Test a package by copying `release/linux-unpacked/resources/next-server` to /tmp and running `node apps/web/server.js`, or launch `release/linux-unpacked/Timely --user-data-dir=/tmp/x` under xvfb with `env -u ELECTRON_RUN_AS_NODE` (the Claude Code shell sets it, and the binary then rejects every Chromium flag as "bad option"). Re-running a failed tag release does not pick up fixes; the tag must be moved or a new version tagged.
- Settings → Server only renders for onboarded accounts; an account created via curl lands on /onboarding first, then the desktop routes to /setup once.

**Why:** each one cost a debugging loop during the first end-to-end run.
**How to apply:** check these before touching the supervisor or the packaged web server; see [timely-worktree-qa-environment](timely-worktree-qa-environment.md) for the general worktree traps.
